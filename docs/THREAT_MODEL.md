# Threat Model

## Chain reader

The scan runs entirely on the user's device, but the queries it makes are not
free of leakage:

- **Blockscout history queries.** Transaction history, token transfers and
  approvals are read per-address from a Blockscout instance (default:
  `eth.blockscout.com` / `base.blockscout.com`). Each query reveals to that
  Blockscout instance which addresses were scanned and when. Queries are made
  one address at a time, but an observer of the instance can still correlate
  the set of queried addresses.
  - Mitigation: the Blockscout base URL is configurable per chain
    (`ChainReaderConfig.blockscoutUrls`), so a user can point the reader at a
    self-hosted Blockscout instance and remove this leakage entirely.
- **RPC queries.** Balance, nonce and ENS reverse lookups go to the user's
  configured RPC (`ETH_RPC_URL`, `BASE_RPC_URL`), or viem's default public
  transports when unset. The provider sees each queried address individually.
  - Mitigation: users pick their own RPC endpoints; running a personal node
    removes the third party.
- **NEAR RPC.** `.near` accounts are checked via `view_account` against
  `rpc.mainnet.near.org` (configurable). The RPC sees the queried account id.
- **Labels are local only.** The exchange label set (dawsbot/eth-labels) and
  the OFAC list (0xB10C) are bundled as static JSON inside `packages/core`.
  Lookups are local `Set`/`Map` reads — the user's address set is never sent
  to a label API.

## AI explainer

Explanations of scan results go to a NEAR AI Cloud model
(`z-ai/glm-5.3-flash`) that serves on NEAR's own TEE fleet
(`provider=near`). Two mitigations bound what this can leak.

**What is sent.** `/api/explain` and the CLI send only a *redacted* report:
every `0x` address is replaced by a stable alias (`Wallet 1`,
`Counterparty 1`, ...), all transaction hashes are dropped, and only check
letter, kind, points, label names (e.g. "Coinbase"), ENS/.near names and
amounts survive. The model never sees a wallet address, a tx hash, or an
address-book link — and it never decides amounts or actions. A unit test
asserts no `0x` address or hash appears in the request body. The route is
stateless: it does not log request bodies, store data, or run analytics.

**API key.** `NEAR_AI_API_KEY` exists only on the server (Next route
handlers) and in the CLI. The browser calls `/api/attestation`, a thin
proxy that adds the key and forwards the client's nonce unchanged — all
verification logic runs in the browser on the returned report. The proxy
cannot choose or alter the nonce.

**What the attestation proves.** With a fresh 32-byte nonce the client
verifies, for the gateway and every `model_attestations[]` candidate:
(1) the Intel DCAP quote is valid and its report data binds our nonce and
the claimed `signing_address`; (2) `request_nonce` echoes ours, so the
report is fresh, not replayed; (3) the quoted RTMR3 equals a replay of the
enclave's `event_log`; (4) `SHA-256(app_compose)` matches the quote's
MRCONFIGID, so the enclave runs the published compose. Together these
prove the response was generated by attested hardware running known code,
and that the report answering *our* request is the one we verified.

**What it does not prove.**

- **Instance ≠ signer.** A matching model signing key does not prove the
  report and the completion came from the same serving instance — NEAR's
  docs warn that instances may share signing keys. A malicious sibling
  instance with the same key could sign a different completion. We still
  require the signature signer to match exactly one verified report, but
  treat this as necessary-not-sufficient.
- **GPU evidence.** NVIDIA GPU attestation payloads are reported as
  "present, not verified" — no open-source verifier is wired in, so GPU
  confidentiality claims are unchecked.
- **DCAP collateral source.** DCAP verification fetches collateral
  (TCB info, QE identity, CRLs) from Phala's public PCCS over HTTPS, in
  both browser and CLI. A down or malicious PCCS can fail verification
  (fail-closed, good) but collateral is served over TLS and the quote
  chain still anchors to the Intel root CA embedded in the library.
- **Model output correctness.** Attestation proves *where* the answer ran,
  not that the answer is right. The model only writes prose; no amounts or
  actions are derived from it.
- **Freshness window.** `request_nonce` equality proves the report is
  fresh for this check, but verification is point-in-time; Re-check is
  manual and issues a new nonce each run.

If any check fails — missing `model_attestations`, a wrong nonce echo, a
mismatched RTMR3 or MRCONFIGID, a bad quote, or a signature whose signer
matches no (or more than one) verified report — the UI hides the AI text
and the CLI exits non-zero.
